# AI 基础 11 模块：每个模块该怎么避免错误

> 基于 [Handbook](https://aiweb3.school/zh/handbook/) 原文整理

---

## 1. LLM

| 常见错误 | 怎么避免 |
|---------|---------|
| 把模型输出当事实 | 关键事实来自数据库/API/链上，模型只是推理层 |
| 代码/JSON 塞满上下文 | 长内容先压缩或交给检索系统按需取回 |
| 模型编造 API、合约地址 | 输出必须接入外部校验：来源引用、schema 校验、规则检查 |
| 截图里的文字被遮挡也信 | 关键判断必须回到结构化数据 |

---

## 2. Prompt

| 常见错误 | 怎么避免 |
|---------|---------|
| 把 prompt 当安全边界 | Prompt 是软约束，真正的边界由代码、权限、校验承担 |
| 指令和用户输入混在一起 | 系统规则、用户目标、检索内容分层放 |
| 输出是自然语言没法检查 | 关键结果用 JSON schema，代码可查可阻断 |
| 没防 Prompt Injection | 外部内容标为不可信 → 工具调用前参数校验 → 高风险人工确认 |
| 模型遇到不确定时瞎编 | Prompt 写清楚：不确定就说"不确定"，别补全 |

---

## 3. Context

| 常见错误 | 怎么避免 |
|---------|---------|
| 把所有东西都塞进上下文 | 分层放置：指令层→任务层→事实层→知识层→外部层 |
| 不可信网页当系统指令 | 外部内容标注来源和可信度，放最底层 |
| 过期数据当最新状态 | 链上数据实时查，文档标日期和版本 |
| Memory 替代实时授权 | 涉及资产/权限的记忆必须重新绑定当前会话 |
| 上下文藏着旧任务状态 | 新任务开始前清理残留，别让上一轮状态泄漏 |

---

## 4. RAG

| 常见错误 | 怎么避免 |
|---------|---------|
| 向量相似就当正确答案 | 相似≠正确，配 metadata 过滤来源、版本、可信度 |
| 旧文档当最新版本 | 每个 chunk 标更新时间，过期的降权或删除 |
| 搜不到就开始编 | 检索失败就拒答，不要让模型补全 |
| 标题相似内容不对 | 用 rerank 按相关性+可信度重排 |
| 结论没出处 | 每条答案附来源链接+日期，用户可验证 |
| 检索延迟太高用户等不住 | 预置固定答案，别硬走 RAG 管道 |

---

## 5. Agent

| 常见错误 | 怎么避免 |
|---------|---------|
| 权限给太大 | 只读自动跑，写入/花钱/签名必须人点确认 |
| 没设停的条件 | 目标达成、预算耗尽、信息不足、越权、用户拒绝→立刻停 |
| 工具调用没日志 | 调用前/后都记录，出事可追溯 |
| 多 Agent 权限蔓延 | 问自己：加更多 Agent 真的减少复杂度了吗？ |
| 状态藏在模型上下文里 | 状态外置，可查询、可恢复、可审计 |
| 多个进程抢同一资源 | 今天亲测：旧 Agent 没关，新 Agent 抢 TG Bot 持续 conflict |

---

## 6. Frameworks

| 常见错误 | 怎么避免 |
|---------|---------|
| 简单任务硬上框架 | 一次 API 调用的任务不需要 Agent 框架 |
| 选了框架换不掉 | 先画清输入→工具→状态→输出→失败路径，再看框架帮了什么 |
| 框架藏了不该藏的复杂度 | 理解框架替你管了哪层、又把哪层藏起来了 |
| 抽象太早 | 直接调 API 能跑通的，先跑通再加框架 |

---

## 7. MCP

| 常见错误 | 怎么避免 |
|---------|---------|
| 工具 schema 写得太模糊 | 明确参数含义、必填字段、是否修改外部状态、失败返回值 |
| 权限只靠协议不管 | 区分只读/写入、会话授权/长期授权、是否需确认 |
| 写入工具没审计记录 | 每次调用记录谁、什么时候、做了什么、结果是什么 |
| 认为 MCP = 安全方案 | MCP 标准化工具入口，不替代账户权限、签名确认、交易模拟 |

---

## 8. Vibe Coding

| 常见错误 | 怎么避免 |
|---------|---------|
| 任务太大没边界 | 越具体越有边界，Agent 越容易产出可审查结果 |
| 上下文给一堆无关文件 | 让 Agent 看对的文件和错误输出，比长篇需求更重要 |
| "看起来对"就当过了 | 跑测试、类型检查、构建、截图——硬验证，不靠感觉 |
| 让 AI 绕过 repo 流程 | Issue → branch → commit → test → review，AI 参与但不跳过 |
| 高风险代码不审查 | 合约、签名、权限、支付不能纯靠 Agent 生成直接上线 |

---

## 9. Fine-tuning

| 常见错误 | 怎么避免 |
|---------|---------|
| 模型效果不好就微调 | 先排查 prompt→上下文→检索→输出格式→模型能力 |
| 没 eval 就开始微调 | 先有 eval，才能判断微调是否真的有效 |
| 标注数据太少（<50 条）| 不够就别微调，写好 prompt + few-shot 更实际 |
| 用微调存实时知识 | 实时状态、价格、文档更新放检索或工具，不放模型参数 |
| 测试集拿去训练 | 评估立刻失去意义，过拟合了自己都不知道 |

---

## 10. Inference

| 常见错误 | 怎么避免 |
|---------|---------|
| 只看模型质量不看成本/延迟 | 四维权衡：质量、成本、延迟、可控性 |
| 模型变了输出也变了 | 封装模型调用，支持 fallback 和灰度 |
| 没脱敏输入输出日志 | 生产环境日志必须脱敏，Token/私钥不进第三方 |
| 推理挂了对用户无感知 | 请求失败要有重试和降级策略，不是白屏等 |
| Agent 场景没算成本放大 | 一次用户请求可能触发多次模型调用，成本×5 ×10 |

---

## 11. Evaluation

| 常见错误 | 怎么避免 |
|---------|---------|
| 凭感觉判断"效果不错" | 30 条样本覆盖正常/边界/恶意/历史 bug |
| 修 A 坏 B | 每次改动重跑旧题（regression test）|
| 只测模型不测整条链路 | 用户关心任务完成度，不是模型榜单分数 |
| LLM-as-Judge 全自动不抽检 | 高风险样本保留人工抽检，定期校准 |
| 线上数据不进 eval | 用户真实反馈→复现→加入 regression set |
